## 1. 选型总览

| # | 决策点 | 结论 | 一句话理由 |
|---|---|---|---|
| D1 | 界面形态 | **Web 前端（挂 sidecar）＋ Blender 视口精灵** | bpy 做不出聊天，sidecar 是现成 HTTP 边界 |
| D2 | 前端技术栈 | **零构建原生 ES module + CSS** | sidecar stdlib-only，不引入 Node 运行前置 |
| D3 | 状态推送 | **插件 POST 事件 ＋ Web 轮询（≥1.5 s）** | SSE/WebSocket 与 stdlib 线程模型不匹配 |
| D4 | 小助手渲染 | Web: CSS `steps()` 精灵表；Blender: GPU 贴图精灵 | 两边共用同一份 PNG＋frames.json |
| D5 | key 存储 | `secrets.json`（0600），环境变量优先 | key 不进 YAML/.blend/trace/git（R-UI-1） |
| D6 | 剧本优化 | 新状态 POLISHING＋人工采纳门 | 复用 human_gate 语义，不新建门种类 |
| D7 | 规则开关 | `SkippedFinding` 哨兵短路＋`skipped` 留痕 | 实证：`_error/_warning` 有 24 个直推调用点，None 方案会把 None 塞进 findings 列表；哨兵让 24 点零改动 |
| D8 | 提示词模板引擎 | stdlib `string.Template`＋`specs/prompt_templates/*.txt` 数据文件 | jinja 在 Blender Python 无保证（NFR-2）；R-痛点 P1 要求模板随目标模型可换——数据文件化即答案 |
| D9 | 目标模型规格 | `specs/target_models.yaml` 数据文件＋loader 严校验 | R-痛点 §4 原文"规格表要做成可更新的数据文件而非硬编码——模型迭代极快" |
| D10 | 新规则严重级 | R020–R025 全部 warning 起步（红线 R-V） | 新检测无实测基数就直接进 error/门，等于拿未校准的尺子判红——先量误报再谈升格 |
| D11 | polish 的 Web 触发执行者 | **sidecar 直接 `call_upstream`**，与 run 内 POLISHING 共用 contracts 里的 schema/prompt 真源 | sidecar→插件没有反向通道（插件只 POST 事件），让 sidecar"转调插件"在架构上不可行；polish 是纯文本调用无需 bpy，而 provider 细节本就归 sidecar |

## 2. D1 界面形态（本版最重的决策）

| 候选 | 优势 | 否决/采纳理由 |
|---|---|---|
| A. 纯 bpy 面板扩展 | 不新增进程 | **否决**。证据：现有 6 个列表型面板已 1,551 行（layer7_ui 实测）；bpy 无富文本、无 Markdown、无滚动聊天流、无输入法友好的多行编辑；Blender 的 UI 线程模型下长文本渲染会卡交互 |
| B. 独立桌面壳（Electron/Tauri） | 体验最好 | **否决**。新增运行时依赖（Node/ Rust 工具链）违背 NFR-2；sidecar 已在 8765 端口提供 HTTP＋token 鉴权（sidecar_server.py:442），浏览器就是壳 |
| C. **Web 前端由 sidecar 回静态文件** | 零新进程、零新依赖、聊天/设置/知识库全都好做 | **采纳**。风险是"sidecar 没起就没界面"——用 R-UI-2 对冲：Web 只是观察者，主链路不依赖它 |
| D. C ＋ 视口精灵 | 用户在 Blender 里也有"它在干活"的在场感 | **采纳为 D1 终案**：重交互在 Web，存在感在视口；精灵可关（`ui.assistant.viewport_sprite`） |

数据通路（证据：sidecar 现有 `_authorised`/路由结构可直接复用）：

```
Blender 插件(driver) ──POST /v1/ui/events──▶ sidecar(8765) ◀──GET /v1/ui/events?since── 浏览器
       │                                          │
       └── 既有 /v1/chat·/v1/retrieve ···         └── 静态 web/（GET /, /static/*）
```

## 3. D2 前端技术栈

| 候选 | 否决/采纳理由 |
|---|---|
| React + Vite（webapp-building 那套） | **否决**。本仓是 Blender 插件，运行机不保证 Node；构建产物还要再管一份 dist。前端只有 4 个页签、交互密度低，框架收益不抵成本 |
| **原生 ES module + 一个 pixel.css** | **采纳**。sidecar `SimpleHTTPRequestHandler` 风格直接回文件；`fetch` 轮询 + Canvas 2D 足够覆盖聊天/轨迹/设置/试检索 |
| 内嵌进面板（Blender 里画 HTML） | 不存在该技术路径，bpy 无 webview |

约束写死：不许引 CDN（离线必须可用）；全部资源 ≤ 1 MB（不含精灵图）。

## 4. D3 状态推送

| 候选 | 否决/采纳理由 |
|---|---|
| SSE（text/event-stream） | **否决**。stdlib `http.server` 默认每请求一线程，长连接挂住线程；多标签页开 3 个就吃掉线程池。为省 1.5 s 延迟不值 |
| WebSocket | **否决**。stdlib 没有，要引入依赖——直接撞 NFR-2 |
| **轮询 `?since=seq`** | **采纳**。1.5–2 s 粒度对"跑到哪了"完全够；实现是既有 GET 路由加一个环形缓冲（TDD §7），契约测试好写 |

## 5. D4 小助手渲染与资产管线

- **一份资产两处用**：`web/assets/assistant/*.png` ＋ `frames.json` 是唯一真源；Blender 侧 `assistant_sprite.py` 直接读同一目录（插件根相对路径），不复制第二份（本仓已在 `camera.side`/`MOVEMENT_TYPES`/`QUALIFIER_KINDS` 上因"各抄一份"栽过三次——sidecar_server.py:519–524 的注释原文）。
- 像素规格 48×48、×4 放大、12 fps：足够表现 Q 版二头身，帧数 4–8 帧/clip 控制美术量。
- 美术来源（PRD 风险 Q1 的落地）：先 `tools/gen_placeholder_sprites.py` 程序生成占位帧跑通全链路；正式帧用 image_generation 按设定图配色出草稿后人工修像，或约像素稿。**状态机、帧表校验、渲染代码全部不依赖正式美术到位**。
- 动画状态直接映射 `DriverState`（TDD §3），**不新造状态词汇**——14(+1) 态一一对应由契约测试钉死，防止"UI 显示一套、内核跑一套"。

## 6. D5 key 存储与流转

```
Web 设置页 ──PUT /v1/ui/secret──▶ sidecar ──写──▶ %APPDATA%/BlockDirector/secrets.json (0600)
                                                       ▲
插件 transport 读 key：env > secrets.json > config.llm.api_key（兼容旧配置）
```

- 为什么不写进现有 YAML 配置：`BLOCKDIRECTOR_CONFIG` 指向的文件常被用户放进项目目录甚至 git（证据：fixtures/local_*.config.yaml 就在仓里），key 落 YAML 等于迟早泄漏；
- 为什么不用系统 keyring：需要 `keyring` 第三方包，Blender Python 无 pip 保证（NFR-2 同因）；0600 文件权限在 NTFS 下由用户目录 ACL 兜底，对本项目的单机场景足够；
- 掩码规则进契约测试（TDD T4），防止某次重构把明文写进响应。

## 7. D6 剧本优化的位置

| 候选 | 否决/采纳理由 |
|---|---|
| 聊天里随口改（无状态） | **否决**。改写稿进不进 PLANNING 就没了审计点，违反"双向留痕"（PRD §3.3） |
| **状态机新状态 POLISHING＋采纳门** | **采纳**。复用 `human_gate_on_plan` 语义；`accepted=false` 时 PLANNING 输入恒为原剧本由状态机保证；golden 回归证明 enabled=false 零行为差（TDD T8） |

成本纪律：Stage P 是**一次**结构化调用，失败一次即回落原剧本（E_POLISH_001）——它是优化项不是必需项，不许像修复回路那样重试吃预算（证据：AGENTS.md §六十，修复回路曾是最大红源）。

## 8. D7 规则开关的落点

`rule_checker.py` 914 行、十余条规则函数，逐个加 `if` 是最差解（漏一个就静默失效）。单点选在 `_finding` 入口（所有 finding 都经它构造，证据：rule_checker.py:51 起）。**v1.7.1 自修订正**：实测 `_error/_warning` 有 24 个直推调用点（:596–658），`_finding` 返回 None 会把 None 直接塞进 findings 列表——改 **哨兵方案**：短路时返回 `SkippedFinding`，`finish()` 统一分流进 `shot_audit.skipped[]`，24 个调用点零改动。改动面 = 哨兵定义＋`_finding` 3 行＋`finish()` 分流 ~10 行，TDD T5 两个方向锁死。

## 9. 显式不做清单（防范围蔓延，同样重要）

1. 不做在线语料编辑/索引重建（门①–⑩链路不许被 UI 绕过）；
2. 不做聊天命令执行（移交事项，带确认门）；
3. 不做多用户/账号体系（单机 loopback）；
4. 不做 Web 端 3D 视口（轨迹俯视 2D 已够回答"人往哪走、机位在哪"）；
5. 不重排现有 6 个 bpy 面板的布局（TDD §8）；
6. **不为任何未落地功能预留零消费者的配置键**（v1.4 P9.4 删死字段的教训）；
7. **不做 R-痛点 §5 的三条硬解**（报告原文边界）：不增强白模动作细节能力、不管成片端残余不一致、不把白模流程强加给该跳过的镜头——M5 的 `skip_white_model` 是声明机制，不是强制流程；
8. 新规则升格 error 不在本版（红线 R-V：warning 起步，实测后用户裁决）。
