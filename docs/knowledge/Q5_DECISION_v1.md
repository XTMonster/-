# Q5 的处置（2026-10-03 17:0x）——**它现在量得出东西了，但那个东西不足以当门**

## 一句话

今天把"逐镜检索缺一整个轴"这个真缺陷修掉了（意图轴进计划、进契约串、进运行证据），
并按协议给可 join 的那一族补了独立标注；结果是 **Q5 的机制第一次真的通**，
但**它想量的那件事（"计划采纳了检索到的理论"）在这条通道上量不出来**——
因为条目的 `q` 自己就点名了被量的字段（新标的 35 条里 **34 条是恒真的**）。
所以本轮**没有**动判据、**没有**动门限，只加了一条**实读数**当诊断，并把三条出路的
数字全部落盘，请你在下一轮拍板。

`{景别,运镜,镜头}` 那一族（旧 70 条）则永远发不出 `镜头=`（焦段在检索那一刻不存在）。

## 新落地的**实读数**（诊断，不参与门）

`tools/knowledge/quality.py::q5_retrieval_join`：把对齐键从"发出的查询串"换成
**"这一镜真的召回了哪条边"**（分子/分母的语义与门限一个字没改）。

```
6 镜那一跑（带意图轴）：13/13 = 1.0000
64 镜那一跑（无意图轴）：23/31 = 0.7419   ← 低于 0.80
```

它**只作诊断**，理由是样本会被单条条目主导：64 镜那跑的 **31 对里有 8 对**来自同一条
`hq_1057`（期望是一串 pan/track/zoom，而 8 个 LS 镜头都是 `固定`）。把 0.7419 读成
"计划采纳率 74%"是**不成立**的——这一点写进了代码注释、`by_entry` 也逐条报出来。

## 三条出路，现在的数字与代价

1. **换对齐键**（本轮已作为诊断落地）：按"检索到的边"对齐，再加**逐条去重**
   （同一对只算一次；或要求 ≥N 条不同的条目），然后才够格当门。
   代价：改 §4.1b 的 Q5 行（判据文本），实现改动小；收益：从"量不到"变成"量得到"。
2. **修夹具的入口形状**（§35.6 早就点过）：条目的 `q` **不得点名被量的字段**
   （即只留 `景别×镜头` 这类预测型，或让期望取自卡片的另一处）。
   代价：重标一轮，且要动协议；收益：Q5 变绿才真的能证明"计划采纳了理论"。
3. **如实维持红**（现状）：判据、门限、oracle 都不动，把它记成
   "机制已通、但这条通道的鉴别力不足"。

**我的建议**：先做 ①（换键＋去重）——它不需要重标就能得到有意义的分子/分母，
而且**它比现在的判据更严**（64 镜那跑在它下面只有 0.7419，仍然红）；
② 作为下一轮的独立 lane（要重标，且当前 GLM 额度只够勉强跑完面板复核）。
③ 不作为推荐，只作为"你不想动规格时"的兜底。
