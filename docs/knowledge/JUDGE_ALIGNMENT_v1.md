# 评委口径对齐方案 v1（清单 A3 / FX-7）

**归属**：本文是清单 §一 **A3** 的第一份归属文档（"至今没有归属文档"的那个问题）。
**卡**：`执行文档v1.5/EXECUTION_PLAN.md` 卡 **P5-T4**。
**性质**：⚖️ **备料**。本文**不改任何判据、阈值、分母、红线**（R-5）。
对齐的口径要不要拿去**重判存量批次**，由用户裁决。

## 1. 问题（为什么要对齐）

同一条查询、同一批案例、同一天，两位评委给出的相关率**差 0.27**：

| 臂/批次 | `deepseek-chat` | `glm-5.3` |
|---|---|---|
| 三臂对照（`docs/evidence/20261006-rerank-shapes/README.md`） | 0.44 – 0.46 | 0.67 – 0.7120 |

判据 `E1 ≥ 0.70`（`tools/knowledge/e1_panel.py:58` `RELEVANT = 4.0`）是**冻结**的，
所以"过没过线"实际上取决于**用哪把尺**。红线不能动 ⇒ 唯一能做的是**对齐判词口径**，
让两把尺尽量量出同一个数。

**当前判词提示词**（`tools/knowledge/e1_panel.py:64-70`，逐字）：

```
你是分镜预演工具的知识检索复核员。下面给你一条**导演查询串**和若干条被检索回来的
**参考案例**。请判断每条案例对这条查询是否**真的相关**（能不能拿来指导这一次拍摄）。
只输出 JSON：{"scores":[{"case_id":"...","score":1-5,"reason":"不超过 20 字"}]}
5=直接相关且可照做；4=相关；3=沾边；2=几乎无关；1=完全无关。
```

问题：**五个档位只有一句话定义，没有锚点样例**。"相关"与"沾边"的边界、
"能照做"要具体到什么程度，两位评委各自脑补 —— 这是 0.27 的最可能来源
（**推断**，未验证；校准本身就是为了验证它）。

### 3.3 每档两条锚点的选法（可复核）

1. 先按 §3.2 的表把候选行号列出来；
2. 在候选里挑"**两位评委差 ≥1 档、且 `reason` 各自写得具体**"的两条（`reason` 空或

3. 两条锚点必须**来自不同查询**（否则只锚了一个语境）；
4. 定下来的两条锚点，把 `query` + `excerpt`（必要时含 `zh` 中文线索）

5. 锚点入提示词后，**提示词 sha256 要记进产物**（沿用 `e1_panel` 既有的

## 4. 术语对齐表（每个维度"算什么 / 不算什么"）

维度沿用提示词那句"5=直接相关且可照做；4=相关；3=沾边；2=几乎无关；1=完全无关"。
下表把**边界**写死（"算什么/不算什么"双语义），供锚点选取与提示词嵌入：

| 档 | 算什么 | **不算**什么（最常见的误判方向） |
|---|---|---|
| **5** | 案例正文给了**可直接照做**的拍法（含具体参数/装置/机位关系），且与本次查询的**同一维度**（如果查询问运镜，案例就得在说运镜） | 只谈美学形容词、不给做法；或做法说的是**别的维度**（查询问运镜，案例在谈打光） |
| **4** | 同一维度上给了**可迁移**的原则或做法，但需要使用者自己补一步落地 | 只是"也提到这个维度"却没有可迁移内容 |
| **3** | **沾边**：不同维度但同一场/同一体裁；或同维度但只提了一句 | 与查询的拍摄意图**方向相反**（那是 2 或 1） |
| **2** | **几乎无关**：共享个别词，但指导不了这次拍摄 | 明确**反对**这一拍法（那要按"反向指导"判，见 5 档的补充规则） |
| **1** | **完全无关**：通用知识、体裁介绍、与拍摄无关 | —— |

> **两条最容易分歧的边界**（校准时要重点看）：
> ① **3 vs 4**："沾边"和"可迁移"的分界——本仓库里 27 条落在这一档（§3.2）；
> ② **2 vs 3**："共享词但指导不了"与"同场不同维度"的分界——29 条落在这一档。

## 5. 20 条校准流程（可执行）

1. **选样**：从 §3.2 的分歧档里**分层抽 20 条**（每档至少 2 条，档内随机、
   随机种子写进报告）；
2. **冻结**：把这 20 条的 `query` / `excerpt` / `zh` 导出成
   `docs/evidence/<run-id>/judge_calibration_set.jsonl`，记 sha256；
3. **盲判**：两位评委（`deepseek-chat`、`glm-5.3`）**各自独立**判一遍，
   互相不可见；GLM 调用**串行**（README 环境约束 F4）；
4. **对照**：出 per-item 差值表（`score_deepseek`、`score_glm`、`diff`、
   两位 `reason` 并排）+ 汇总（均值差、绝对差中位数、档位一致率）；
5. **定锚点**：对着差值最大的 5 条，人工读两位的 `reason`，判断"分歧是因为
   **定义不同**还是**读错案例**"；只把"定义不同"那几条转成 §3.3 的锚点；
6. **复测**：把锚点嵌进提示词（`prompt_sha256` 记档），对**同一批 20 条**再判一次；
7. **判定**：`|均值差| < 0.10` ⇒ 对齐成功，交用户决定是否重判存量批次；
   否则如实记录，**不许调目标**。

**通道与退路**（README 环境约束）：

* GLM-5.3：**串行**；单次超时/失败按"重试一次 → 仍失败则记 `skipped` 并继续"；
* Kimi：余额挂起（429），**不作为本流程的评委**；
* GPT-6A：仅显式回退，不进默认链路；
* **GLM 不可用 ⇒ 只保留本文件，不跑校准**（卡文原文），报告里写明"未跑 + 原因"。

**本批执行状态（实测）**：本会话进程内 `GLM_API_KEY` **未继承**（`$env:GLM_API_KEY` 为空；
用户级环境变量存在但未注入本进程）。按卡文"GLM 不可用 ⇒ 只出文档不跑校准"，
**本批未跑 20 条校准**，也未产出 `judge_calibration_set.jsonl`。
