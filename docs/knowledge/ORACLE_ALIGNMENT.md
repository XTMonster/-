# held-out 期望与索引的对齐度（实测 · 2026-10-01）

`fixtures/knowledge_holdout.jsonl` 的 `must` 是**看不到索引**的标注员写的；
门⑪现在要求 `norm_key` **完全相等**。两者天生错位。这份文件把四种口径分开量出来，
因为"门该按哪种关系判"是**规格裁决**，不是实现能自选的（协议 §2.3 与 §2.3c 的
两段话在这里互相拉扯）。

复现命令：

```powershell
python tools/knowledge/oracle_alignment.py --json work/oracle_alignment.json
```

## 一、四种关系的定义

| 口径 | 含义 | 谁说得清 |
|---|---|---|
| `exact` | 成员集**完全相等**（现行门⑪） | 需要标注方猜到抽取器选的可选槽位 |
| `subset` | 索引那条边的 plain 成员 ⊇ 标注的成员，且 forbid 集相等 | 标注方只给"下界"即可 |
| `card_subset` | `subset` ＋ **来自同一张卡** | 同上，且要求是这张卡的边 |
| `card_edge` | **这张卡在索引里有没有边**（不看类型、不看成员） | 标注方只要说对"是哪张卡" |

## 二、实测（旧一轮 oracle 4539 条 × 当前索引 683 条边）

| 口径 | `must` 命中 | `top1` 命中 | **Q2 天花板**（至少一条 must 可解析的条目占比） |
|---|---|---|---|
| `exact` | 36.6% | 37.5% | **39.6%** |
| `subset` | 41.1% | 41.0% | **43.5%** |
| `card_subset` | 2.8% | 2.7% | **3.1%** |
| `card_edge` | 93.9% | 94.1% | **94.1%** |

验收线：Q1 ≥ 0.70、Q2 ≥ 0.90、Q4 = 1.0、Q6b = 1.0。

## 三、结论

1. **`exact` 口径下有 60% 的条目从构造上就不可能过**：标注方看不到索引，
   猜不中可选槽位。这不是排序问题——同一条 lane 的实测是"候选集内目标边
   名次中位数 = 1"，说明**排序已经对了，是期望本身落不到索引上**。
2. **`subset` 只多 4 个百分点**（39.6% → 43.5%），因为成员值本身仍然要逐字相同。
3. **`card_subset` 反而最低（3.1%）**：同一张卡里，标注方与抽取器选的值几乎不重合
   ——"要求同卡 + 成员吻合"是最苛刻的一种组合。
4. **`card_edge` = 94.1%**：这是"独立标注 + 不看到索引"前提下**唯一自洽**的期望定义：
   标注方说的是"这条查询应该把这张卡的知识召回来"，而不是"抽取器必须恰好选了我
   猜的那些槽位"。它仍然不是同义反复——标注方依旧看不到索引里有没有边、选了哪些成员。

## 四、没有选它的理由（留给规格裁决）

`card_edge` 放宽了"必须命中**哪条边**"这一条，只要求命中**来自该卡的任何边**。
它换来的是可达到的天花板（94%），代价是：如果一张卡抽出了与研究问题无关的边，
这条 oracle 仍会判"命中"。**这个取舍必须由规格裁决，实现不得自选**——
本文件提供的是做出该裁决所需的四个数，而不是替它做决定。

## 五、门⑪已经在三种口径下跑通（默认仍是 exact）

`tools/check_holdout.py --expectation-relation {exact|subset|card_edge}`：
实测（同一份 oracle × 683 条边的索引）：

| 口径 | 门⑪ status | `must` 解析数 | strict | subset | card |
|---|---|---|---|---|---|
| `exact`（默认） | fail | 1846 / 5043 | 5096 | 5666 | 9010 |
| `subset` | fail | 2075 / 5043 | 5096 | 5666 | 9010 |
| `card_edge` | fail | **4739 / 5043** | 5096 | 5666 | 9010 |

（strict/subset/card 三列是**不随口径变化**的诊断量，分母是全部 13713 条 spec。）

### 5.1 剩下那 6% 是什么

即使切到最宽的 `card_edge`，仍有 **304 条 `must` 解析不到**，对应约 **268 条目**
（= 5.9%），它们指向的不是"值写错"，而是 **86 张在索引里根本没有边的卡**：
这些卡讲的是**单一维度的知识**（只有构图规则、没有景别/镜头/机位；
或只有一句禁令、没有情绪上下文），而**没有任何边类型的必填槽位**能由它们填满。
这类知识目前的归宿是**卡片通道（BM25）**，不是耦合超边。

所以要让门⑪ 真正 100% 通过，只有两条路，都必须规格拍板：

1. **扩 schema**：允许"单维边"，或按 `docs/knowledge/FORBID_COVERAGE.md`
   把 `forbid` 放到本来就有该槽位的边类型上；
2. **让 oracle 能声明"这张卡不承载耦合"**（例如 `must: []` + 具名理由），
   门⑥/门⑪ 对这类条目单独记账——**不能让它们静默消失**，否则覆盖率会造假。

两条都不做的话，`card_edge` 口径把天花板从 39.6% 抬到 **94.1%**，
但门⑪ 仍会如实判红在那 5.9% 上——这是数据，不是缺陷。

## 六、Q1/Q2 的真正天花板：**种子可达性**，不是扩展预算、也不是排序

三种解释都试过并量过：

| 假说 | 实测 | 结论 |
|---|---|---|
| "扩展上限太小，目标边没进候选集" | `tools/knowledge/expansion_caps.py`：上限 ×2 → 候选 37→70 条，命中 0.375→0.380；×4 → 116 条，0.380；再加一跳 → 149 条，0.386 | **几乎无收益**，只会拿精度换 0.5pp |
| "排序不好，目标边在候选集里但排不上去" | 同一条 lane 的实测：候选集内目标边名次**中位数 = 1** | **排序已经对了** |
| "oracle 与索引的取值对不上" | `must` 能进候选集的 query 只有 **1703/4539 = 0.375**；门⑨ 另有 970/4539 条 `q` 连自己 `must[0]` 的槽位都没写全 | **就是它** |

所以 **Q1/Q2 的上限 ≈ 0.38**，与实现无关：标注方写的取值（`q` 与 `must`）
与抽取器选的取值，是两个互不可见的读者对**同一张卡**的独立判断，
一致率只有三成。要让 Q1≥0.70 / Q2≥0.90 可达，oracle 必须换一种写法——
而这与"标注方不可见索引"这条独立性规则**直接冲突**，属规格级取舍：

* **A. 保持独立**：接受 Q1/Q2 上限 ~0.38，把这两条线按现状重新标定；
* **B. 让标注方看到该卡的原子边**：`q` 从边成员派生 → 上限接近 1，
  但这时 Q1/Q2 测的是**排序**（≥0.90 才有意义），不再是"召不召得回"；
* **C. 混合**：`must` 保持独立（用于覆盖率），另设一组**派生自索引**的
  query 用于 Q1/Q2，两组分别报告、互不冒充。

C 是三者里唯一既保住"覆盖门独立"又让排序指标可测的做法，代价是 oracle
要维护两套条目。**选哪一条要用户拍板；实现不替它选。**

### 6.1 一个被我漏掉的成因：`intensity` 没有查询键（已修，附实测）

我第一次判"要不要给 `intensity` 加查询键"时只量了**可达性**：579/579 条边都
至少有一个可挂种子的成员、0 条只挂在缺键槽位上 → 结论是"加了没用"。
**这个结论是错的**，因为它漏了**区分度**：同一类型里大量近邻边**只差一个
`intensity`**（`sfx=静默 + pacing=medium + intensity=low` 与
`…+ intensity=mid` 是完全不同的两条边）。查询说不出"强度"时它们无法区分，
排序只能交给 occurrences/confidence —— 抽 4 例失败样本，**4 例都是输给"只差
强度"的兄弟边**。

实测（`tools/knowledge/ranking_quality.py`，全量 683 条索引派生查询）：

| 键 | Q1 | Q2 |
|---|---|---|
| 现状（无 `强度`） | 0.6164 | 0.8653 |
| **+`强度`** | **0.7189** | **0.9165** |
| ＋`头留白`／`平均镜长` | 0.6574 | 0.8668 |

**只加 `强度`**：Q1/Q2 双双越过 0.70/0.90 线；再加那两个键反而回落（键多了会
把更有区分度的成员挤出查询串的前三位），所以按实测只加一个。

### 6.2 复查那两个键：上一条的"回落"是**查询构造**的假象

上面那句"挤出前三位"本身就是提示：派生查询只取**前 3 个**可查询成员时，
新键完全可能排在第 4 位而被截掉——用它判"新键有没有用"是把方法学的坑当结论。
`ranking_quality.query_for(..., wanted=N)` 现在可配，用**全部可查询成员**（N=6）
重测：

| 键集 | 只取 3 个成员 | 取全部成员 |
|---|---|---|
| 现状（含 `强度`） | Q1 0.7189 / Q2 0.9165 | **Q1 0.7555 / Q2 0.9488** |
| ＋`头留白`／`平均镜长` | 0.6574 / 0.8668 | 0.7496 / **0.9575** |

取全部成员时两者几乎打平（Q1 −0.6pp、Q2 +0.9pp，n=683 的标准误约 ±1.6%），
**所以维持"只加 `强度`"**：那两个键要么是噪声级差异，要么换来门③/门⑨ 又一轮
覆盖（9 个取值），不划算。结论没变，但**依据换成了公平的那一版**。

顺带得到一个有用的读数：**查询写全时排序是 0.7555 / 0.9488**——即"给足约束，
排序能力已经在线（Q1/Q2 线是 0.70/0.90）"；剩下的差距在**查询本身写得够不够全**。

代价（如实记）：门⑨ 的"够不着"从 **970 条涨到 2449 条（21.4% → 54.0%）**——
这不是新缺陷，而是**新键把原本藏着的弱查询暴露出来了**：现有 4539 条 oracle
是在没有这个键的时代写的，说不出强度。标注提示是**从 schema 渲染**的
（`check_holdout.queryable_slot_hint`），所以下一轮标注会自动带上 `强度`，
门⑨ 随之收敛；在那之前它如实判红。
