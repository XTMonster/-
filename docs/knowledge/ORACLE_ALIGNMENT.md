# held-out 期望与索引的对齐度（实测 · 2026-10-01）

`fixtures/knowledge_holdout.jsonl` 的 `must` 是**看不到索引**的标注员写的；
门⑪现在要求 `norm_key` **完全相等**。两者天生错位。这份文件把四种口径分开量出来，
因为"门该按哪种关系判"是**规格裁决**，不是实现能自选的（协议 §2.3 与 §2.3c 的
两段话在这里互相拉扯）。

复现命令：

```powershell
python tools/knowledge/oracle_alignment.py --json work/oracle_alignment.json
```

## 一、四种关系的定义

| 口径 | 含义 | 谁说得清 |
|---|---|---|
| `exact` | 成员集**完全相等**（现行门⑪） | 需要标注方猜到抽取器选的可选槽位 |
| `subset` | 索引那条边的 plain 成员 ⊇ 标注的成员，且 forbid 集相等 | 标注方只给"下界"即可 |
| `card_subset` | `subset` ＋ **来自同一张卡** | 同上，且要求是这张卡的边 |
| `card_edge` | **这张卡在索引里有没有边**（不看类型、不看成员） | 标注方只要说对"是哪张卡" |

## 二、实测（旧一轮 oracle 4539 条 × 当前索引 683 条边）

| 口径 | `must` 命中 | `top1` 命中 | **Q2 天花板**（至少一条 must 可解析的条目占比） |
|---|---|---|---|
| `exact` | 36.6% | 37.5% | **39.6%** |
| `subset` | 41.1% | 41.0% | **43.5%** |
| `card_subset` | 2.8% | 2.7% | **3.1%** |
| `card_edge` | 93.9% | 94.1% | **94.1%** |

验收线：Q1 ≥ 0.70、Q2 ≥ 0.90、Q4 = 1.0、Q6b = 1.0。

## 三、结论

1. **`exact` 口径下有 60% 的条目从构造上就不可能过**：标注方看不到索引，
   猜不中可选槽位。这不是排序问题——同一条 lane 的实测是"候选集内目标边
   名次中位数 = 1"，说明**排序已经对了，是期望本身落不到索引上**。
2. **`subset` 只多 4 个百分点**（39.6% → 43.5%），因为成员值本身仍然要逐字相同。
3. **`card_subset` 反而最低（3.1%）**：同一张卡里，标注方与抽取器选的值几乎不重合
   ——"要求同卡 + 成员吻合"是最苛刻的一种组合。
4. **`card_edge` = 94.1%**：这是"独立标注 + 不看到索引"前提下**唯一自洽**的期望定义：
   标注方说的是"这条查询应该把这张卡的知识召回来"，而不是"抽取器必须恰好选了我
   猜的那些槽位"。它仍然不是同义反复——标注方依旧看不到索引里有没有边、选了哪些成员。

## 四、没有选它的理由（留给规格裁决）

`card_edge` 放宽了"必须命中**哪条边**"这一条，只要求命中**来自该卡的任何边**。
它换来的是可达到的天花板（94%），代价是：如果一张卡抽出了与研究问题无关的边，
这条 oracle 仍会判"命中"。**这个取舍必须由规格裁决，实现不得自选**——
本文件提供的是做出该裁决所需的四个数，而不是替它做决定。
