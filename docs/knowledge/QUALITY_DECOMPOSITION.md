# Q1/Q2/Q4/Q6b 的**可分解性**：线到底是没达到，还是根本没被问到

角色视角：**测试与验收**。只读探针 `.scratch/metric_probe.py`，在**当前索引**
（766 边 / `extract/v10`）与**当前 held-out**（2927 条）上跑 `tools/holdout_score.py`。

## 一、三个测量

| 测量 | 样本 | Q1 ≥0.70 | Q2 ≥0.90 | Q3 ≤0.10 | Q4 =1.0 | Q6a | Q6b =1.0 | Q7 =1.0 |
|---|---|---|---|---|---|---|---|---|
| **A** 原样（入库的那份 oracle） | 2927 | 0.6437 ✗ | 0.7646 ✗ | 0.0 ✓ | 0.9892 ✗ | 1.0 ✓ | 0.9986 ✗ | 1.0 ✓ |
| **B** 只留 `must`／`top1`／`never` **全部能在索引里解析**的条目 | **1185** | **0.8025 ✓** | **1.0 ✓** | 0.0 ✓ | **1.0 ✓** | 1.0 ✓ | **1.0 ✓** | 1.0 ✓ |
| **C** 空集（分母下界） | 0 | fail | fail | fail | fail | fail | fail | fail |

## 二、怎么读这三个数

1. **C 说明"空集通过"这个洞已经堵上**（§4.1b 硬规则 1）：七个指标在零样本上全部判
   `fail`，不是恒真。
2. **B 说明实现本身**（BM25 打分 ＋ 超图查询解析 ＋ 三栏注入）**能够同时满足四条线**：
   Q1 0.80、Q2 1.00、Q4 1.00、Q6b 1.00。
3. **A 与 B 的差**就是"oracle 与索引不同构"的代价：2927 − 1185 = **1742 条**条目的
   `must`／`top1`／`never` 里有指向**不存在**的边的规格（`required_unresolved`），
   它们把 Q1/Q2/Q4/Q6b 从"达标"拖到"不达标"。

**因此：Q1/Q2/Q4/Q6b 现在红，测的是"这份 oracle 是不是对着当前索引写的"，
不是"检索排序好不好"。** 这也解释了为什么上一轮反复调 `SCORE_WEIGHTS` 到不了线。

## 三、这条结论**不能**被过度解读（如实写）

* **B 是条件测量**：它按"能不能解析"筛过样本，而"能解析"本身与"标注当时走得顺"
  相关，所以 **B 不是全量 oracle 排序质量的无偏估计**。它证明的是
  "**实现的能达到线**"（能力），不是"换个 oracle 就一定达标"（预测）。
* 若要拿到无偏的达标证据，仍然只能**用当前索引重标一轮**（`glm_v12` 正在做），
  然后在**全量**上跑 A 那一栏。
* B 里 `Q3 = 0.0`（负样本零误命中）与 A 相同，说明负样本的构造没被筛影响。

## 四、对门⑥ 的连带影响

门⑥ 的情境与此对称：它的 72 张缺口里，**27 张卡在索引里一条原子边都没有**
（其中 26 张**在构造上抽不出来**，见 `GATE6_STRUCTURAL_FLOOR.md`），其余 45 张
随重标会消化。所以这一轮之后，**Q 组四线有望全绿，门⑥ 会停在结构下限附近**——
两者不是同一类问题：前者是"标注对不对齐索引"，后者是"许可语料里有没有那类知识"。
