# "gpt6A 有点问题"是对的：**请求会被丢掉后静默挂着**——而且**没有单次上限**让它挂满 6 小时

日期 2026-10-06 20:5x。用户原话："**感觉 gpt6A 有点问题，运行了那么久还没有结果**"。
本目录把这句话变成可复算的读数与一处修复。

## 一、诊断：不是"慢"，是**静默挂死**

同一秒（18:34:45）发出、**同样 1.3–1.8 KB 的包**、**同样 `max_tokens=32768` 与
`reasoning_effort=max`** 的三个请求：

| 请求 | 结果 |
|---|---|
| `c_arch` | **3.4 分钟**返回正文（806 B） |
| `a_metric` | **5.1 分钟**返回正文（857 B） |
| **`b_closeout`** | **137 分钟**，`.log` **0 字节**；`dRead=0/40s`、`dCpu=0/40s`、连接 `Established` |

⇒ **同输入、同参数、同瞬间**：两个回来了，第三个**一个字节都没收到**。
**它是被丢掉了，不是在思考。**（20:53 已掐掉。）

**为什么本机看不出区别**：中转站的流式响应**没有 keepalive**——"在思考但没出字"与
"被丢掉、永不出字"在客户端**长得一模一样**。

## 二、根因（真正造成伤害的那一半）：**单次尝试没有上限**

socket 超时是**每次读**的超时 ⇒ 它实际就是"多久没收到任何字节就放弃这次尝试"。
而调用方给的是**总预算**：

* `work/_gpt6a_ask.py --timeout 21600` ⇒ 一个静默请求会占着位置到 **6 小时**；
* `tools/relay_consult.py::consult` 还**重试 3 次**、每次同样 6 小时 ⇒ **最坏 18 小时**。

这就是"运行了那么久还没有结果"的机制：**它不是慢，是没人给它设放弃线。**

## 三、修复（代码，已加守门）

`tools/relay_consult.py`：

* 新增**单次尝试的"无数据上限"** `attempt_timeout`（默认 `1800 s`），实际用
  `min(总预算, attempt_timeout)`；传 `0` 可显式退回旧行为（给长文生成留的出口，但**默认不是它**）；
* **每次尝试新建客户端**——把超时留下的 socket 丢掉，不复用；
* 上限写进 `usage.attempt_timeout_s` 与每次失败记录（**可审计**）；
* `work/_gpt6a_ask.py` 增加 `--attempt-timeout`（问询脚本用 **900 s**）。

守门：`tests/test_llm_relay.py` 两条——① 每次尝试按 `min(总预算, 上限)` 建客户端、
且**每次新客户端**、上限进 usage；② `attempt_timeout=0` 时才退回旧行为。
全量：**2380 passed / 1 skipped**。

## 四、顺带抓到：**巡查任务自己发起了重复请求**

掐掉的那件（pid 51912，19:18:45 起、100 分钟零字节）问的是
`work/_q_gpt6a_decides.md`——**与主线同一意图**（"你是验收方，请直接下决定"），
而它是**本仓库的定时巡查任务**发起的（它本该"只观察"）。
⇒ **重复占用通道**，而且用的是**旧的无上限封装**，所以也挂住了。

**处置**：巡查任务已改成**只观察**——不许跑 `_gpt6a_ask.py`、不许写新问题、不许改仓库；
发现为空只**报告**，由主线重新发起。

## 五、留下的行为

现在发出去的每一件咨询：**900 s 没数据就放弃这次尝试并重试**（最多 3 次）
⇒ 最坏约 **45 分钟**一定会给出**明确结果或明确失败**，不会再无声无息挂 1.7 小时。
**这与"给 gpt6A 更多时间"不冲突**：上限是**单次无数据**的，不是总时长——只要数据在流，
它就一直等（长文生成因此不受影响，可用 `attempt_timeout=0` 显式放行）。

## 七、**勘误**（2026-10-06 21:4x）：我把"最坏多久"算错了一倍

我在上一节写过"按新包络**最坏约 45 分钟**必有结果或明确失败"。**这是错的。**

对回源码：`RelayClient.chat()`（`tools/kb_fetch/llm.py:603-617`）在一次 `chat` 里
**先走流式**（`_stream`，每次读超时 ＝ `attempt_timeout`），**失败后还会退回非流式**
（`_post`，**同一个**超时）。也就是说 —— **一次 `chat()` 最坏 ≈ 2 × `attempt_timeout`**。
而 `relay_consult.consult` 又**重试 3 次**（各建新客户端）⇒

```
最坏 = 3 次 × (流式 900 s ＋ 非流式 900 s) ≈ 5400 s = **90 分钟**
```

**可观测的迹象**：那条裁定请求到 **46 分钟**还在跑——**在 90 分钟包络之内**，
不是"没生效"，是我把包络说小了一半。

**这条勘误只改口径，不改代码**：`attempt_timeout` 仍按设计生效（单次**无数据**上限），
只是"最坏总时长"要按 `6 × attempt_timeout` 报。**要收紧就把 `attempt_timeout` 调小**
（例如 300 s ⇒ 最坏 ~30 分钟），**但它同时会缩短"合法长生成"的耐心**——
两者是同一个旋钮，按需取舍，别默认改。
