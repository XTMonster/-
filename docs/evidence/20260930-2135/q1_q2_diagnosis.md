## 3. Q1/Q2 的差距定位（抽 400 条逐条追踪）

| 情形 | 条数 | 含义 |
|---|---|---|
| 命中 top-1 | 37 | 真命中 |
| 命中 top-20 但掉出 top-3 | 64 | **排序问题**（边在候选集里） |
| 根本没进候选（未扩展） | 23 | **查询根本指不到那条边** |

未扩展那 23 条的典型形态：`must` 写 `AXIS_RULE:pair=any_two,axis_side=left`，而 `q` 里
**没有任何轴线取值**（例：`q="景别=MS；镜头=85mm"`）。索引只有 `pair`/`axis_side` 两个
成员，查询里没有轴线的种子 ⇒ 这条边永远召不到。
按协议 §3.1 的定义，`must` 是"**必须能从这条查询检出**"的边——这些条目本身**不合约**，
是标注侧写错，不是检索器的问题。

排序那 64 条的成因与规格一致：`查询节点覆盖率 = |边成员 ∩ 种子节点集| / |种子节点集|
（§2.3 第 3 步、line 768）`，当查询只覆盖到目标边的一个侧面（例如只写 `景别`，而目标边
还含 `轴线`）时，它的覆盖分量必然低于"覆盖两个种子的邻边"。**线本身不能动**
（Q1≥70%/Q2≥90% 是验收线），所以出路只有两条：

1. **标注侧收紧**：`must` 里的每条边必须与 `q` 至少共享一个**具体取值**（而不是只共享
   `pair=any_two` 这种 schema 常量）。这条目前**没有**在 `absorb()`/门② 里强制，
   属于"协议写了、机器没查"。
2. **检索侧排序**：在不动覆盖率定义的前提下，把"查询里出现过、且属于该边专有成员"的
   信号（例如 `composition_rule`/`intent` 这类判别性强的 kind）加权，压过全局的
   `type_priority`/`occurrences`/`authority` 三项——后者与查询无关，是当前并列过多的主因。

下一步会先做 ①（让 oracle 自洽），再看 Q1/Q2 的剩余差距用 ② 收。
