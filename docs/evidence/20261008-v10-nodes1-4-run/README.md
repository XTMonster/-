## 3. 为什么这么慢：**83.6 分钟里 83.4 分钟在等模型**

按 `llm_trace.jsonl` 的 `duration_s` 逐次统计（同一条 trace 里既有耗时也有 prompt）：

| 用途 | 次数 | 最短 | 中位 | 最长 | 合计 |
|---|---|---|---|---|---|
| understand | 1 | 96.6 s | 96.6 s | 96.6 s | 96.6 s |
| plan | 1 | 107.9 s | 107.9 s | 107.9 s | 107.9 s |
| editor（逐镜起草） | 13 | 54.9 s | 116.9 s | 175.6 s | 1519.6 s |
| repair（定向修复） | 5 | 90.4 s | 186.3 s | **900.2 s** | 2212.8 s |
| react（受限精修） | 5 | 3.5 s | 60.2 s | **900.2 s** | 1065.3 s |
| **合计** | **25** | | | | **5002 s ＝ 83.4 min** |

三条根因，按贡献排序：

1. **超时白等占了 45 分钟（2700 s ＝ 整跑的 54%）**：3 次 `E_LLM_001 连接失败: timed out`，
   每次都是把 **900 s 的预算原样烧完**。这三次分别发生在 `shot_002` 的两轮修复与一次
   ReAct 精修上——超时之后驱动**重试同一条提示**（第 2 次），又超时，于是该镜 `shot_degraded`。
2. **通道本身是"慢思考"**：百炼上这个部署**默认就在想**（实测 `reasoning_effort` 裸 / `max`
   的 reasoning token 是 497 / 466，旋钮改不动量级，见 `docs/evidence/20261007-v15-bailian/`），
   空问题就要 9–14 s；这里每次调用还背着 RAG 三栏 ＋ 4 节点全文 ⇒ 中位 **117 s/次**。
   横向对照：同一通道的 **6 镜**那一跑是 2500 s（≈7 min/镜），本跑 13 镜量级一致。
3. **调用次数是镜数的约两倍**：13 次起草 ＋ 11 次审核 ＋ 5 次修复 ＋ 5 次 ReAct ＝ 25 次以上，
   而**每一次返工都付全额延迟**（没有"短提示快速试探"这类便宜路径）。

本地计算不是瓶颈：场景构建 1.6 s ×2、检索 14 次都在 0.1 s 量级、审核（射线/构图）秒级。
**结论：把通道换快（或把 thinking 关掉）是唯一有量级意义的提速**；其余都是零头。

## 4. 缺陷与问题清单（每条：现象 → 证据 → 根因 → 修法 → 严重度）

### ① 默认单次调用超时 120 s 对"思考档"模型根本不成立 —— **高**

* 现象：第一跑（`work/_run_nodes1_4.log` 的那次之前的尝试）**计划调用第一次就 `E_LLM_001 timed out`**，
  驱动重试第 2 次（`llm_request 请求分镜计划（第 2 次尝试）`）。
* 根因：`DriverLimits.llm_timeout_s = 120.0`（`block_director/layer5_orchestrator/driver.py:85`）是**代码默认**，
  `config.llm.sidecar_timeout_s` 也是 120；**面板里没有这一格**，只有 `tools/run_headless.py --llm-timeout`
  有（它的帮助文本自己写着"本地大模型常需放大到 600+"）。
* 修法：把这一格提到面板/配置层（`llm.timeout_s`），并给"慢通道"一个**建议值**；本轮我是在驱动脚本里
  显式传 `--llm-timeout 900` 才跑起来的（**这算绕过产品缺格，不算用产品**）。

### ② 超时后的重试策略是"原样再等一遍" —— **高**

* 现象：`repair_failed 修复调用失败（第 1 次）…timed out` → 紧接着
  `llm_request 请求修复 shot_002（第 2 次）` → 又是 900 s → `shot_degraded`。两次合计 **30 分钟**。
* 根因：超时被当成"网络抖动"，重试用**同一条提示、同一个超时**；没有"缩小输入 / 换便宜档 / 直接降级"的阶梯。
* 修法：超时重试要么**缩短输入**（去掉 RAG 大块、只留该镜），要么**降档**（`tool_choice` 已是 auto，
  可再降 `reasoning_effort`——但那要用户点头，属"换脑子不换标准"的显式决策），要么**立刻降级**而不是再赌一次。

### ③ 工具 schema 与模型的世界模型对不上（可修，且高频） —— **高**

* 现象 A：`draft_invalid` ×4，全是同一个字段：`hand_to 的 toward 必须是数字（当前 '木围栏'）`、
  `（当前 'camera'）`、`（当前 [0.7, 1.1, 0.3]）` —— 模型按"语义目标"填，schema 要"单个数字"。
* 现象 B：`react_invalid` ×2：`stand 不认识的参数 ['base_z']`、
  `turn_body 不认识的参数 ['speed','toward','yaw_d…']` —— 模型按它对动作的直觉命名参数。
* 现象 C：`repair_invalid` ×2：`第 1 个拍点的 subject='char_01' 不在本镜角色里` ——
  模型用的是**场景对象 id**（`char_001`），而修复接口按**计划里的角色名**校验（同一份契约两套 id 空间）。
* 根因：工具描述只给"键名 + 类型"，没给**坐标系约定、单位、允许键表**与一两个正例/反例；
  且 `char_01` vs `米迦尔` 这类 id/name 映射对模型不可见。
* 修法：① 工具 schema 里补 `description` 与 `enum`（允许键表已在报错里生成，直接前置到工具描述）；
  ② 修复接口接受两种 id 并**内部归一**（`char_01` → 本镜角色名）或在错误信息里回显合法值；
  ③ 给 `hand_to.toward` 一个显式的"目标点"结构（`{"character": "米迦尔"}` 或 `{"point": [x,y,z]}`）。

### ④ 构图门在这一份剧本上**系统性不过**（不是偶发） —— **高（质量）**

* 读数：11 次审核里 `E_CAM_001`（构图分 < 70）**9 次**，分数 **46.4 / 46.4 / 46.4 / 60.3 ×4 / 30.4**；
  `E_AXIS_001`（R001 越轴）**10 次**。
* 后果：`shot_002` 等 3 镜已经 `shot_degraded`——**降级继续**意味着这些镜会带着已知问题进交付包。
* 根因假设（**未验证**，需要下一步证伪）：本剧本的**空间尺度**（偷盗者要跑开、市场拱廊很长）
  与 `config.scene.extent_m = 12 m` 的场景可用范围、以及 `拍摄距离 → 景别 → 构图求解` 那条链
  在这套机位下解不出可过门的构图；v15 台账里"构图门 20→32"那几刀修的是**锚点**（按该镜首帧人在哪摆机位），
  这份剧本的角色走位更散，锚点规则可能又不够用了。
* 证伪动作：用**零 LLM** 的路线重放这一跑的 `audit_log.jsonl`（`layer9_persistence/replay.py`），
  对每个失败镜打印"角色包围盒 / 机位 / 该镜首帧目标点 / 构图分四项分量"，看是**机位摆错**还是**求解器没解**。

### ⑤ RAG 硬约束栏把"条件模式"当无条件禁令发出去 —— **中**

* 读数：13 镜全部拿到 `禁={…}`，4 镜的"违反"正是**剧本写死的** CU/dolly_in（详见
  `docs/evidence/20261008-v10-nodes1-4-rag/README.md` §3）。
* 根因：`SHOT_PATTERN` 边是**条件取反**（"MS＋50mm＋变焦 ⇒ 别用 CU"），检索按 `景别=` 命中、
  渲染层一律写成「必须（除非声明破例）」。
* 修法：渲染层区分"无条件禁令"与"条件模式的取反"（后者只进【经验建议（软）】栏或写成"若…则…"）。

### ⑥ 三栏注入在真实数据上退化成 1–2 栏 —— **中**（上限已按用户裁决抬到 5 万/6 万，
但**实测只抬上限不改注入量**：真正卡住的是 `top_k=5` / `rule_top_k=5` / `cases_top_k=3`）

### ⑦ 无人值守路径下 `request_self_review` 没有承接者 —— **中**

* 现象：`self_review_requested shot_003 已登记自我审核` ×2，随后什么也没发生（GUI 里这一步等于"提示用户去看"）。
* 影响：后台/批处理跑（正是用户在用的方式）时，模型主动要求人看的那些镜**静默通过**。
* 修法：把"待人工复核"落成**产物**（`shots.json` 里一个 `needs_review: true` ＋ 交付 README 里汇总），
  而不是只挂在驱动器的内存状态上。

### ⑧ `scene_built` 出现两次（内容逐字段相同） —— **低（待确认）**

* 读数：两条 `scene_built`，都是 `shots:13, characters:4, cameras:13`，耗时 1.608 s / 1.549 s。
* 影响：多花 1.5 s（可忽略），但**要确认**不是"编辑后又整场重建"——那会在大场景里变成分钟级。

### ⑨ 交付包还没出，且**墙钟会先撞线** —— **高（本轮实际风险）**

* 读数：83.6 min 已用 / 120 min 上限；还是**审到第 4 镜**（共 13 镜）。
* 若撞线，驱动 CANCELLED，**这一跑的 25 次调用全部作废**（没有交付包）。

## 8. 检索宽度取多少：**主线按实测定的值**（用户 2026-10-08："你帮我决定合理的数值"）

先在**合法区间**里扫参（`work/_rag_width_probe.py`，真索引、真查询、不调模型）。
合法区间来自 `AppConfig.validate()`：`rule_top_k` **只能 3–8**（`CFG_020`）；`top_k > 0` 无上界；
`cases_top_k` 无校验但注释写 2–5。（**上一轮我拿 `rule_top_k=20` 出的那组数是非法的**，作废。）

  （计划提示里只剩硬约束栏）。10 只把量翻倍，栏还是缺。
* 不选 20/30/50 的理由是**可证伪的**：代表"强命中"的边数**恒为 5 条**，再往上全是只命中一格的
  擦边（20 时 25%、50 时 12.5%）。**为了把那 5–6 万的上限填满，就得灌 90% 以上的弱材料**——
  那是"更吵"，不是"更懂"。

  **E1 证书的"产品语境"**（`PRODUCT_CONTEXT`），改它＝改一门现役验收读数的语境，
  要连带重发 E1 证书 ⇒ 属用户决策，不混在这一刀里。
* 上限（50000/60000）从此只是**安全网**，不会再成为约束；`≤ 上限` 这条验收不变量照旧成立。
