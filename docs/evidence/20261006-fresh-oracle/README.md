# **决定性结论**："完美重排上限 0.8438"拿不到——**重新盲评**那 3 条只有 **0.4583**

日期 2026-10-06 09:38。这一步是给 R3 那条红线做**终审**的。

## 做法

把每条查询的**oracle 三元组**（＝池子里原标签分最高的 3 条）拿出来，**当成一个新的三元组
重新盲评**一次（同两位评委、同判分提示词，与 `e1_panel` 同一份 `judge()`）。

```powershell
python work/_probe_oracle_triple.py      # 64 条查询 × 2 评委（顺序跑，约 40 min）
```

## 读数（同一批 64 条查询）

| 口径 | 值 |
|---|---|
| **"完美重排上限"**（原标签里 `min(3, 相关行数)/3` 的均值） | **0.8438**（162/192） |
| **把 oracle 三元组重新盲评**后的 E1 | **0.4583**（88/192） |

⇒ **差了 0.3855。** 也就是说：**哪怕重排器完美地挑出"标签说最好的那 3 条"，
在真实判分语境下也只有 0.4583。**

## 为什么（机制）

那条 0.8438 是**数出来的**：它数的是"池子里有 48 条候选，其中多少条**在各自原来的三元组里**
被标过相关"。而 E1 判的是**重排器自己凑出来的那个三元组**——
本仓已实测评委给分**随同批候选变化**（`docs/evidence/20261006-e1-judge-context/`：
同检索、同内容，只因调用里塞的候选条数不同，两位评委同向漂移 0.18→0.32）。
**一条"在弱兄弟旁边看着不错"的案例，被放进另一个三元组就不再≥4。**
⇒ **上限那一格不是"可达目标"，它只是一个计数。**

## 这条结论改变了什么（三句话）

1. **当前测量协议下，E1 的可达上界约为 0.46**（这 64 条查询上），**不是 0.84**。
2. **实测最好的重排器（LLM `select`＋线索 0.44）已经拿到可达上界的约 96%** ——
   **缺口不在重排器上**。之前把 0.44 当成"只拿到上限 52%"是拿错了分母。
3. **0.70 靠换/训重排器到不了**。要到 0.70 只有两条路：
   ① **换更好的候选**（更深的池子／更好的案例层：让"最好的 3 条"本身就更好，
   这是唯一还没被证伪的工程方向，需要给更深池子做标签才能量）；
   ② **动测量协议**（判分语境/口径）——那是**红线**，要用户拍板。

## 未验证 / 边界（如实挂）

* 只做了 **64 条查询**（就是"上限 0.8438"那一批），**没有**在其他查询集上复验。
* oracle 三元组只从那一次 k=50 池子的标签里取；**更深/更好的池子可能有更好的"最好 3 条"**
  ⇒ 可达上界本身可能被试高或试低，这条**没测**（要测得先给更深池子打标签）。
* 这一步只判 192 行、**没有重复跑**。

## 附：**免费**的先验证据——相关案例**没有**在 rank 48 处枯竭

用现成的 k=50 标签（行序＝检索序）把相关行按检索名次分三档（每档 16 名）：

| 检索名次 | 相关行 | 该档行数 | 相关率 |
|---|---|---|---|
| 1–16 | 144 | 1024 | 0.1406 |
| 17–32 | 65 | 1024 | 0.0635 |
| **33–48** | **70** | 1024 | **0.0684** |

⇒ **最深的那一档还有 70 条相关行**，而且相关率**没有继续掉**（0.063→0.068，平了）。
这说明"相关案例在 rank 48 处就被挖完了"不成立 ⇒ **更深的池子应该还能给出更多相关候选**，
也就是"换更好的候选"这条路**有先验支持**（不是空想）。

## 追加（2026-10-06 20:1x，P14-263）：**补齐原件**——结果发现这个 0.4583 **重跑不出来**

### 1. 先说个证据洞：这个数的原件**根本不在库里**

上面那个 **0.4583（88/192）** 是**承重**的——RK-13 的整个论证（"当前协议下可达上界约 0.46，
不是 0.84"）都架在它上面。但原实现 `work/_probe_oracle_triple.py` **只打印汇总、不落盘**，
而 `work/` 又是 gitignore 的 ⇒ **任何地方都没有这次判分的原始分数**。
一个**不可复算**的承重数字，正是本仓反复收口的那类洞（cf. 只活在 `work/` 下的问题包）。

### 2. 补齐 ＋ 重跑（`reviews.oracle_triple.json`，`probe_oracle_triple2.py`）

除"写盘"外**一切照旧**（同一份 `--labels`、同一条"按标签分取前 3、并列按 `case_id`"、
同两位评委、同一个冻结的 `e1_panel.judge`），并同时记两种口径：

| 口径 | 分子/分母 | 值 |
|---|---|---|
| 原 README 报的（**一次**读数） | 88/192 | **0.4583** |
| 本次重跑 · `loose`（与原来同口径：按答上来的评委取均值） | 81/192 | **0.4219** |
| 本次重跑 · `strict`（P14-249 的两位评委口径） | 77/192（5 行只有一位评委） | **0.4010** |

⇒ **同一个测量重跑一次，差了 0.0364（7 行）**。0.4583 **不是**一个可复现到优于 ~±0.04 的数。

逐三元组分布（`loose`）：`0 相关 10` / `1 相关 32` / `2 相关 17` / **`3 相关 5`**
——**5 条查询的 oracle 三元组拿到 3/3**，所以"3/3 在池子里存在"这条在**这条路径上也成立**
（与 `20261006-e1-triple-ceiling/` 的组装探针给的 4 条互相印证）。

### 3. 这改变什么、不改变什么

* **不改变**结论的方向：0.40～0.46 全都在 0.70 之下很远，"靠换/训重排器到不了 0.70"照旧成立。
* **改变**的是这句话的强度：台账里"可达上界 ≈ 0.46"应当读作
  **"可达上界约 0.40～0.46（单次读数之间差 ~0.04）"**——它是个**带噪声带的区间**，
  不是一个点估计。任何拿它做**小数点后两位**推理的地方都要按这个带宽重读。
* 与本仓既有的噪声结论一致（同一条命令重跑，30% 的行分数会变）。

### 4. 未验证

* 只重跑了**一次**（没有做多轮取均值）。0.4583 与 0.4219 谁更接近真值**没有定论**——
  能说的只有"**单次读数的散布约 ±0.04**"。
* 本文只覆盖**这一批 64 条查询**、这一份索引。
