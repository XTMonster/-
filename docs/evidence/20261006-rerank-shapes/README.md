# 重排提示词形状与"给不给中文线索"：**select + 线索**最好（0.4479 / 0.4375）

日期 2026-10-06 06:37。同一批 64 条冻结查询、同一语料（`48df4a53`）、同一批评委、
同一通道（`deepseek-chat`，用户规则：重排只用 GLM／DeepSeek）、同一深池
（`--rerank-retrieve-k 50 --top-k 3`）。**只改一件事**：重排提示词的形状／候选清单里给不给中文线索。

## 读数

| 配置 | `cases_rerank` 自述标签 | **官方口径（两位均值 ≥4）** | 只 deepseek 评委 | **只 glm 评委（跨族）** |
|---|---|---|---|---|
| `order`（全序排序） | `deepseek-chat/order@8192` | **0.2760**（53/192） | 0.2460 | 0.5215 |
| `select`（只挑 3 条） | `deepseek-chat/select@8192` | **0.4115 / 0.4167** | 0.4255 / 0.4121 | 0.6557 / 0.6684 |
| `score`（逐条 0–10） | `deepseek-chat/score@8192` | **0.4293**（82/191） | 0.4350 | 0.6811 |
| **`select` ＋中文线索** | `deepseek-chat/select@8192+clue` | **0.4479 / 0.4375** | 0.4583 / 0.4427 | 0.6667 / **0.7120** |

（`select` 那行是 P14-222 已入库的读数，列在这里做对照；`order`/`score`/两跑 clue 是本目录新增。）

## 三条结论

1. **"让模型排全序"是最差的形状**（0.2760）：50 条候选排全序对它太难。
   `select`（只挑最该看的 3 条）与 `score`（逐条打分）都好得多，**`select` ＋线索最好**。
2. **把中文线索交给重排器确实有用**：`select` 0.4115/0.4167 → `select+clue` **0.4479/0.4375**
   （＋0.03 上下）。这与"查询是中文、摘录是英文，重排器却看不到案例层本来就有的中文对齐面"
   这条**信息缺口**的诊断一致。
3. **两位评委会为同一批输出打得很不一样**：同 192 行上，`deepseek` 评委 0.44–0.46、
   `glm` 评委 **0.67–0.71**，**差 0.27**。官方口径是两者均值 ⇒ 它落在两个评委中间。

## 这条"评委分歧"要单独记账（它现在挡着红线）

红线的判据**不能动**（两位评委 1–5 分别取均值 ≥4.0）。但这意味着：

| 读法 | `select+clue` 的最好一跑 |
|---|---|
| **官方口径（均值）** | **0.4375**（离 0.70 差 0.26） |
| 只跨族评委（glm） | **0.7120**（**已过线**） |
| 只同族评委（deepseek，＝重排器那一族） | 0.4427 |

⇒ **"过没过线"现在取决于用哪把尺**，而两把尺差 0.27——这已经不是"重排器还差一点"，
而是**判分器本身的分辨率问题**。第三方（Kimi）在 2026-10-06 的判词里也点到过：
「Kimi 强制 temperature=1 ⇒ 噪声不能调没，只能重复取样压掉」。
**未做**：把两位评委的**判据（不是阈值）**对齐一次（例如要求它们各自先写出"这条为什么相关"
再打分），看那 0.27 是"真分歧"还是"打分习惯"。**这不是改判据**，是让两位评委按同一套解释打分。

## 未验证 / 风险

* `select+clue` 只跑了 2 次（0.4479 / 0.4375，极差 0.0104）。
* `order`／`score` 各只 1 次（`order` 明显更差，`score` 与 `select` 同档）。
* **线索之外，重排器还看不到 `title`**（评委看得到）——这是**下一处信息缺口**，见 P14-224。
* 官方口径离 0.70 还差 0.26：**这一条不能被"跨族评委 0.71"掩盖**。
