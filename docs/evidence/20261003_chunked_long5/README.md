# `20261003_chunked_long5` — `camera.side` 变成闭集之后的那一跑

`20261003_chunked_long4` 暴露"模型把 `camera.side` 写成整句中文、求解器静默折成
`front`"之后修的（commit `e7182da`）。这一跑用来验证修法的**契约层**效果与**质量层**
效果——两者结论不同，都要如实记。

## 结果

```
run_id （见 run_manifest.json）   DONE / 64 镜 / built=true   llm_calls 298
draft_received 65 / draft_invalid 0
side 取值：front_left 24 / front_right 9 / over_shoulder 8 / right 7 / left 6 / back_right 4 …
           —— **64 条全部是合法 token**（run4 里只有 12 条，其余是中文句子）
构图分：中位 51.5、≥70 的 28/221；64/64 镜仍判失败
```

## 两个结论（分开说，别混）

1. **契约层：修好了。** 模型的取景意图不再是"一段没人看得懂的中文"，而是求解器真能
   用的 9 个方位之一——这是"意图可表达"的前提（此前所有非 token 的取值都被**静默**
   折成 `front`，等于把模型的每一个角度选择都丢掉）。
2. **质量层：没有回升。** 构图分中位 57.7 → **51.5**。结合 run4 的归因（`三分线交点`
   157 次、`视线留白` 80 次），说明"折成 front"**不是**构图分低的主因：模型自己挑的
   角度（front_left/over_shoulder 之类）在当前的求解器+评分模型下并不更好。
   下一步要动的是**求解器与评分模型的对齐**（以及"运动镜头怎么算构图"），
   不是继续调提示词。

**反面教训一条**：修好一个契约（"意图能表达"）不等于修好一个指标
（"构图分更高"）——把两者混在一句话里汇报，就会得出"修了反而变差"的错觉。
