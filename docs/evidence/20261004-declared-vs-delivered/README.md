# 声明 vs 交付：**40 / 64 镜**的运镜与分镜表声明不符（决策项，附数字）

## 一句话

分镜表为 **63 / 64** 镜声明"固定镜头"，而交付的场景里 **40 / 64** 镜有相机运动
（`dolly_in` 14、`dolly_out` 14、`handheld` 5、`push_through` 3、`zoom_in` 2、
`crane_up` 1、`steadicam` 1）。**没有一镜**是"声明了非固定运镜却没做"。

两边都在**同一份交付产物**里，不需要重跑：

* **声明侧**：`export/shots.json` 的 `declared.technique`（例：`"固定镜头"`）。
* **交付侧**：同一条目里的 `movements[].kind`（`_applied_movements` 同源）。
* **交叉验证**：`audit_log.jsonl` 的逐镜 `retrieval_call.data.query` 里

  `拍摄手法` 分布（`{固定镜头: 63, 微推: 1}`）一致。**声明侧没有丢**。

## 谁把运镜放进去的（追溯）

`movements[].source` 的分布：`planned` 23、`theory` 14、`lesson` 3、**`declared` 1**。

也就是说 40 次"声明固定却动了"里，只有 1 次是"剧本声明的那个运镜"（那一镜声明的是
`微推`，走的是 `declared`），其余是**计划/草案/知识**给的。这与代码一致：
`driver._pin_declared_camera` 明写"B1 已经给了运镜时不覆盖：那才是落实侧"，
而 `static` 因为"引擎运镜词表里没有'固定'"被直接跳过——所以"声明固定"这一档
**没有任何环节去落实或核对**。

## 它与 Q5 的关系（不是巧合）

链上 Q5 现在读本代长跑（§八十四），结果 **9 / 12 = 0.75**（线 0.80）。那 3 条不通过的

而标注的期望是 `固定` 那一族；交付动了之后，这一对在账上只能算"没采纳"。
**Q5 差的这 0.05 就是这条声明缺口**。

## 两条出路（都要用户拍板，**都不许调门限**）

1. **声明绑定**（与台词 pin 同族）：分镜表写了"固定镜头"就不许给这一镜加相机运动。
   收益：交付忠于分镜表；Q5 的 3 条不通过自然消失（12 对里 12 对同值）。
   代价：这一版的片子会变成"63 镜固定机位"；构图门的实测影响**未知**（v1.2 §10.4 说
   构图那一项靠 `side` 而不是靠运镜，但没在 64 镜上量过）。
2. **计划决定运镜**：让阶段 A 逐镜声明运镜（它已经拿到整场知识预取），逐镜查询串
   于是**如实地**带着它，B1 只负责执行。收益：Q5 量的才真的是"计划采纳了理论"，
   检索注入的知识也与这一镜将要做的事一致。代价：计划阶段的 schema／提示词要扩，
   而它是**一次调用出 64 镜**，多一个字段有拖垮计划质量的风险。

两条都不做也**不是**降级——只是把"合不合规"继续留给读者判断；但那样 Q5 会一直停在
0.75，而**原因不在检索、也不在修复回路**。
