## 0. 一句话

结案文书里唯一**没有真判支撑**的承重墙是"**池子挖深到 12 就有救**"这条结论——

## 1. 判什么（逐条口径）

| 项 | 口径 |
|---|---|
| 查询集 | **64 条 held-out 查询**（冻结集，与 E1 同源） |
| 臂 | `retrieval_order@12`（检索原序前 12 条）——**这是"挖深池子"这条路的本体**；另有 3 条嵌入臂与 1 条 `label_top` 阳性对照作陪跑（可只跑本体） |
| 判什么 | 对每条查询，**枚举池内 C(12,3)=220 个三元组**，每个三元组**整组（C=3 语境）**交两位评委逐案打 1–5 分 |
| 怎么算相关 | 两位评委均值 **≥ 4.0**（与 `e1_panel.RELEVANT` 同源，**判据一个字没动**）；"漏一位评委不发分"沿用 P14-249 |
| 要回答的问题 | 深度-12 的**真判**上界是多少；它能否够到 **135/192 = 0.703125** |

**实测锚点（`docs/evidence/20261006-pool-depth-ceiling/pool_ceiling.json`）**

```
queries = 64        threshold_135_of_192 = 0.703125
retrieval_order@12  ceiling = 0.5365     embed3:title+excerpt+zh@12 = 0.5312

```

⇒ 深度-12 的 proxy 上界 **0.5365 < 0.703125**，离门还差 **0.1666**。

## 3. 预计成本（**实测锚 + 线性外推**，外推部分标注为估）

**实测锚**（仓内唯一的时间数字，来自 `RK13_CLOSEOUT.md` §5 与历次面板运行）：

```
192 行（＝64 查询 × C=3 的 3 条）两位评委判完 ≈ 1 h 50 m（串行）
⇒ 约 0.573 分钟 / 行
```

**要判的量**：

```
64 查询 × C(12,3)=220 组 × 3 行/组 = 42,240 行
```

**外推（估）**：

| 并发 | 预计墙钟 |
|---|---|
| 1（串行） | ≈ **403 h**（42,240 × 0.573 min） |
| 6 路 | ≈ **67 h** |
| 10 路 | ≈ **40 h** |

> 仅跑"本体臂"（`retrieval_order@12`）就是上面的量；再加 3 条嵌入臂与阳性对照则 ×5。
> 这正是 `RK13_CLOSEOUT.md` §5"**价格没锚**"那条理由的量化版本。

**token 成本（估，量级）**：每次三元组调用 ≈ 3 案 ×（标题 60 ＋ 摘录 220 字符）≈ 1.2k 输入 token；
`14,080` 次调用 × 2 评委 ≈ **34M 输入 token**（输出按每次 ≤ 200 token 估 ≈ 5.6M）。
**这是估**：仓内没有逐行 token 台账，要精确必须先跑 20 条试点并记 usage。
