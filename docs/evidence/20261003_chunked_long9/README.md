## R003：幻影 vs 真实（这是本跑最硬的一条）

把 R003 的 finding 按"消息里出现了**两个不同**镜号"分类：

| | run8（修前） | **run9（修后）** |
|---|---|---|
| **跨镜**（幻影：规则看错帧区间造出来的） | **154** | **0** |
| 同镜（模型自己排的重叠，真实） | 333 | 233 |
| 命中镜数 | 64 / 64 | 45 / 64 |

修法是一次**单向、可判定**的改动：`cinema/schedule.py::action_frame_window` 成为
折算动作帧的**唯一真源**（`start ≥ 1`、`end ∈ [start, duration]`），
`shot_builder.action_requests`（构建）与 `rule_checker._action_ranges`（规则）
都改用它——此前只有构建器夹、规则不夹，于是模型把 `end_frame` 写到时长之外时，
规则报出"`shot_055` 的动作溢出到 `shot_056`"这种**场景里并不存在**的重叠。

`temperature 0.2` 的逐镜草案每跑都不同，`R001/R003/构图` 的分布随之整体平移。
所以：

* **引擎侧的修复**用"成对重建/同一份工程前后对拍"来量（lane 的 0.423→0.984、
  154→0 都属于这一类，可复算、与模型无关）；
* **端到端通过率**要多次跑取分布才能比较——单跑差异（19 vs 0）主要是**模型方差**，
  不是"哪一处修复把它弄坏了"。真想拿它当验收线，得先定"跑几次、取什么统计量"，
  那是规格裁决。

## 下一层的两个方向（都由本跑的分布指出来）

1. **同镜重叠（R003 233、45 镜）**：模型排的动作区间真的重叠。可以做的是
   把"这一镜里每个动作的窗口"像对白那样**摊开给它看**（`dialogue_budget` 的同款做法），
   或在解析期**拒绝重叠的草案并把原因回灌**（`character_action` 工具早就这么拒，
   草案这条路还没接上——两条路对同一条规则的执行不一致）。后者要连带决定
   "B1 草案被拒时是**重试这一镜**还是沿用计划"，属循环形状裁决。
2. **R001 61 条 / 21 镜**：轴侧优先已经接进 `camera_direction`（`81e99ba`），
   run8 的 79 → run9 的 61；剩下的多半是**多镜之间的连续性**（反打/中性机位的
   交替），需要一次专门的轴侧审计，而不是继续在单镜里找。
