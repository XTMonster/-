每镜交付的 3 条案例**整组重判**（C=3、两位评委均值 ≥4.0、分母＝交付条数、红线 0.70）。

## 为什么会反过来（第三条"proxy 骗人"的证据）

proxy 那把尺子把"一条案例相关"定义为"**它在银行里**（top-120，按**连续三连**判出来的）
那一格的分 ≥4.0"。而 **E1 判的是重排器自己凑出来的那个三元组**——本仓已实测评委给分
**随同批候选变化**（`docs/evidence/20261006-e1-judge-context/`：同检索同内容，只因一次调用
喂的候选条数不同，0.18→0.32）。于是：

* **现役那一列 proxy 与官方逐位吻合**（0.1719 vs 0.1771）——因为交付的那一组**就是**银行里的
  那一组，两种数法数的是**同一个三元组**；
* **重排后没有任何一条银行记录对应"重排器挑出来的那 3 条"** ⇒ 只能拿逐案例分去**近似** ⇒
  近似在这里**错了号**。

⇒ 这是一条**可复用的纪律**（前两次同形：微调的代理口径 0.5625 vs 真实 0.3542；
完美重排上限 0.8438 vs 重判 0.4583）：
**"在别的三元组里被标过相关"不能当作"它被交付时仍相关"的证据**，
凡是要改"交付哪 3 条"的臂，**必须整组重判**才算数。

## 未验证 / 边界（如实挂）

1. 只测了 `embedding-3` **原样余弦**（被编码文本＝案例的中文线索，无线索退回英文摘录）；
   **没有**测"查询改写 / 线索加权 / 混合 BM25 / 去冗余"这些重排形状 ⇒ 本目录能支持的
   说法只是"**原样余弦重排在交付位是负的**"，不是"嵌入这条路死了"。
2. 两臂都只跑了 **1 次**（没有重复跑）⇒ 没有跑间极差；而现役那 0.1771 是**认证版**，
   与它比是跨文件比较（同索引、同查询集、同面板、同语境，指纹都在行里）。
3. `judge_incomplete` 行数三臂不同（9 / 3 / 8）——它不是"谁更稳"的证据，
   **只是通道抖动**；官方口径把它们留在分母里（方向只会让读数更低）。
4. 驱动脚本 `probe_cloud_arm.py`（同目录留档，原型副本在 `work/_e1_cloud_arm.py`）**未进冻结清单**：
   它只**组装**冻结仪器的公开缝，但"云端档"还没接进 `e1_panel.load_embedder`。
   要把这条臂变成**可复算的官方读数**，得再做一次显式的重新冻结。
