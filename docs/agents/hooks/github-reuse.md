## GitHub 复用检查（先找现成方案，再决定自研）

本次请求被判定为**设计 / 规划 / 执行文档 / 程序设计**类（触发词：`{{HITS}}`）。
按用户裁决（2026-10-05）：**这一类在动手之前，必须先去 GitHub 看有没有可利用的现成方案；
有可用的就用。** 这不是建议，是这一轮的**硬步骤**。

### 必须做的事（顺序固定）

1. **全量检索，不是按需搜索**：至少 3 组检索词，每组覆盖"任务名 ＋ 关键约束"，
   例如 `<领域> <问题> library` / `<算法名> python` / `<格式> parser`；
   必要时再按语言、许可证、最近更新时间过滤。**检索面要写下来**，别只留结论。
2. **候选清单（≥3 条，不足要说明为什么）——但"调研"与"判断能不能魔改"
   **是同一个动作**：每读到一个候选就**当场**过一遍下面的"本项目实际约束表"
   （§4b），并把结论**直接写进这张表的最后两列**。不许先攒一堆候选、最后再回头想
   "能不能改"——那会把"魔改可行性"变成事后辩解。

   | owner/repo（URL） | ★ / 最近提交 | 许可证 | 匹配点 | 不匹配点 | **①能否直接用** | **②魔改后能否用**（四档之一：`①原生满足／②改上游即可满足／③改上游也满足不了／④只有改我们的需求才能用`，**④ 按弃用处理**；并附改造点／量级／上游可跟踪／依赖代价／衍生许可） |
   | --- | --- | --- | --- | --- | --- | --- |
   | … | … | … | … | … | 是／否 ＋ 一句理由 | 是／否 ＋ 一句理由（**撞了哪条本项目约束**） |
3. **许可证门**（与仓库既有语料门同一纪律）：
   `MIT / Apache-2.0 / BSD / ISC / MPL-2.0` 这一类可引入；
   `GPL / AGPL / 无许可证 / 来源不明` **不得引入本仓库**（除非用户明示并写进 ADR）；
   厂商 SDK 额外看"是否要密钥、能否离线、是否锁死版本"。
4. **决定与理由（四选一：从候选表的最后两列**直接读出**，不另起一节；
   "全盘复制"和"自己写"之间还有**魔改**这一档）**：

   | 选项 | 什么时候选 | 必须留下的证 |
   | --- | --- | --- |
   | ① **直接采用**（当依赖／引用） | 接口与数据模型对得上 | 版本锁定方式 ＋ 许可证 ＋ 出处 |
   | ② **魔改后采用**（fork／局部改造／**移植其中一段**） | 主体能用，只有一到几处对不上 | **改造点清单**（`文件:函数`）＋ **改造量级** ＋ **上游版本与 commit** ＋ **patch/fork 策略** ＋ **衍生许可** ＋ **魔改后的验收** |
   | ③ **弃用** | 关键约束对不上 | 哪条约束 ＋ **为什么魔改也不划算** |
   | ④ **自研** | ①②③ 都写清之后 | 自研**成本**与**验收判据** |

   **魔改可行性（选了 ② 就必须逐条回答）**：
   1. **改造点**：改哪几个文件／函数？**对外接口变不变**？
   2. **改造量级**：几处、大约多少行？**超过"接口层的一层薄适配"就要说明为什么这不算自研**
      （把它的图模型翻译成我们的槽位模型，那层翻译就是我们既有的逻辑——**这类魔改要诚实记为
      "改造量 ≈ 自研"**，别拿它冒充复用）。
   3. **上游可跟踪**：上游更新后还能合并吗（fork ＋ 定期 rebase ／ 维护一份 patch）？
      还是注定分叉、以后只能自己走？
   4. **依赖代价**：魔改之后**还要不要拉进它的整条依赖链**？如果只用到"一个文件／一段算法"，
      优先**把那一段移植过来 ＋ 注明出处**，而不是把整库拉进来。
   5. **衍生许可**（衍生的门槛比原样用更严）：
      `MIT / BSD / ISC` 可改可再分发，**必须保留版权声明与许可证全文**；
      `Apache-2.0` 同上 ＋ **保留 NOTICE（若有）＋ 标明改动**；
      `MPL-2.0` 改动的**文件**需同许可公开；
      **`GPL / AGPL` 有传染性 ⇒ 不得引入本仓库**（AGPL 连"提供网络服务"也算）；
      **无许可证／NOASSERTION：既不能复制也不能改**（默认保留全部权利）。
   6. **魔改后的验收**：跑本仓库全套测试与验收链；**不许**因魔改放宽／删除本仓库的判据
      （判据与阈值**一字不动**）；把"与上游的差异"落成 patch／diff 或至少一份差异清单。

   **两条边界**：**魔改 ≠ 重写**（改造量≈自研就如实记）；**魔改 ≠ 降级**（借别人的代码
   不是放宽验收的理由）。

   ### 4a. 魔改＝**按本项目需求**改（需求是基准，不是上游的形状）

   魔改的方向**只有一个**：**我们的需求要什么，就对着需求改**。不是"看上游能提供什么，
   然后我们迁就它"。

   1. **先把需求写成可验收的条目**（R1…Rn）：来源＝本轮请求 ＋ 执行文档里的验收判据
      （门①–⑩／Q·E 指标）＋ 用户裁决。**不许自己发明需求**，也**不许把上游的某个 feature
      当成需求**。
   2. **逐条对候选打分（四档，标签自带方向，防"改谁"的歧义）**：
      `①原生满足`（上游原样就能满足）／
      `②改上游即可满足`（**只改上游的代码**：改造点可定位、量级小）／
      `③改上游也满足不了`（缺能力或撞本项目硬约束——写清**缺的是什么**，不要只写"不合适"）／
      `④只有改我们的需求才能用`（**这一档不算满足**：它意味着需求被打折）。

      **歧义澄清（2026-10-05 用户指出）**：这里的"改"**一律指改上游**；"一段"指
      **改造量级**（几处、几行），**不是**"改一段需求"。凡是"只有改我们的**需求／判据**
      才能用上"的方案，**记 ④ 并按③弃用处理**——需求优先，**不许**写成"能满足"。
   3. **写"改成什么形状"**：对着需求给出**目标接口／数据结构**（例：我们要
      `retrieve(query, top_k) -> cases`，就把它改成这个签名），同时列出**改造点**
      （`文件:函数`）与**与上游的差异清单**。
   4. **需求优先**：**不许为了迁就上游而改需求**。某条需求在魔改后打了折，必须写成
      "该需求不可满足 ＋ 代价"交回主线／用户，**不许静默降级**（与《强制执行契约》第 4 节同源）。
   5. **验收**：需求条目**逐条对拍** ＋ 本仓库既有链（§4c）——不是"能跑就行"。

   ### 4b. 魔改判断必须对着**本项目当前的实际情况**（先读真源，再判；不许凭印象）

   这张表就是第 2 步里**当场**填「②魔改后能否用」那一列时用的判据，
   **不是事后复盘的清单**：看到一个候选就过一遍，逐条写结论。

   **先读这三份真源**（每轮都读，别背旧结论）：
   `AGENTS.md` 的「最新，以这行为准」状态块（当前门/指标/`pytest`/探针数）、
   `docs/knowledge/ACCEPTANCE_STATUS.md`（未收口项与待裁决）、
   `pyproject.toml`（当前**零运行时依赖**）。

   **然后逐条过这张表**——每条写：`不适用` / `代价是什么` / `直接出局`：

   | 本项目的硬约束 | 现状（2026-10-05） | 对候选的含义 |
   | --- | --- | --- |
   | **插件跑在 Blender 自带的 Python 里** | Blender 5.2 / Python 3.13；连 `rank_bm25` 都没有，BM25 是手写的 | 任何要 `torch`／向量库／embedding／编译扩展的方案**进不了插件进程**，只能进 **sidecar**（独立进程）或**构建期** |
   | **零运行时依赖** | `pyproject.toml` 里没有 `dependencies` | 引入依赖＝破坏承诺，必须写明代价与隔离方式（sidecar ／ 构建期） |
   | **确定性与可重放** | RK-17 逐帧 1e-6、replay 零 LLM 调用、六元指纹 manifest | 模型版本／随机性／浮点差异会威胁可重放 ⇒ 构建期可用，运行时慎用 |
   | **判据一个字不许动** | 门①–⑩、Q0–Q7／E1–E3、32/32 探针、`pytest` 全绿 | 魔改后必须**原样**过链；不许因引入而放宽任何一条 |
   | **许可门** | 语料白名单（CC0/CC-BY/CC-BY-SA/PublicDomain/OwnWork/ExplicitPermission）；代码侧 MIT/Apache-2.0/BSD/ISC/MPL-2.0 | GPL／AGPL／无证**直接出局**（**"只改一点"也不行**） |
   | **自研规模与数据模型已定** | `hypergraph.py` 68 KB ＋ `build_hypergraph.py` 134 KB；2353 卡／638 边／16 类边／**槽位＋冻结词表＋契约串** | "改上游去适配我们的槽位模型"＝写一层翻译器 ≈ 重写既有匹配逻辑 ⇒ 记**"改造量 ≈ 自研"** |
| **本机资源与可用模型** | RTX 4070 Ti SUPER 16 GB／32 GB；执行与普通子代理使用**当前会话选择的模型（不固定）**；独立 GLM-5.3 等通道按 `model-routing.md`；本地 `torch+CUDA` 与 `bge-small-zh-v1.5` 已缓存（sidecar 可用） | 拿哪个通道做 embedding **都要先探**（别凭印象）；本地 embedding 只能进 **sidecar**，插件进程仍零依赖（这条已实测过：`e1_panel --cases-rerank embedding` 就是在 sidecar venv 里跑的） |
   | **当前真实瓶颈** | 红门是 **E1（语料适配度 0.1441 对 0.70）** 与 RK-13，**不是**"检索框架不够强" | 魔改的优先级排在"语料／查询同层"之后；别为框架而框架 |

   **落笔格式（每个候选一行，缺列不算做完）**：

   ```
   候选 | ①能否直接用 | ②魔改点与量级 | ③撞了哪条本项目约束 | ④结论(采用/魔改/弃用/自研) | ⑤证据(文件:行号 / 命令)
   ```

   **反例（本项目的真实判例，ADR-0014）**：`HyperGraphRAG` 的"魔改"被否，
   **不是**因为"改不动"，而是因为它撞了两条本项目硬约束——Blender 的 Python 装不了
   `torch`／`neo4j`／向量库；而"改它去适配我们的槽位模型"要写的一层翻译器
   **就是我们既有的匹配逻辑**（改造量 ≈ 自研）。这就是"按本项目实际情况判"的样子。

   ### 4c. 魔改的验收判据＝本仓库现有的链

   魔改完成不等于"能跑就行"：必须**原样**通过本仓库的验收链
   （门①–⑩ ＋ `pytest` ＋ 探针清单），并在 ADR 里写清"**没有降低任何既有判据**"；
   同时把与上游的差异落成 patch／diff 或差异清单（含上游 commit）。
5. **落证**：候选清单与决定写进当次的执行文档／ADR；草稿可放 `work/`（草稿区、不进库）。
   结论是 ① 或 ② 时，把 **上游仓库 ＋ commit hash ＋ 许可证 ＋ 改造点（若 ②）** 一并写进
   `docs/knowledge/LICENSES.md` 一类的地方。
6. **引入之后不改验收**：跑本仓库的测试与验收链；**不许**因"别人的代码"就删测试、
   跳测试、放宽阈值——这条与《强制执行契约》第 4 节同源。

### 两条容易忘的边界

* **"别人的代码"不等于"别人的思想"**：算法／思路可以借鉴公开工作，但**代码出处与
  许可证必须留痕**；反过来，只写"参考了 X"而**实际拷了 X 的代码**是不允许的。
* **联不上网或检索不到时**：如实写"本次无法检索／无可用方案"与**试过的检索词**，
  不得把"没查"写成"查过没有"；网络不可用时明确写进 `not_checked`。

### 与自动会诊的关系

设计／规划／难题这一轮**同时**触发《模型分工契约》的联合会诊。顺序固定为：

1. 先做 **GitHub 复用检查**（上面 1–4 步，出候选清单与决定）；
2. 把这份清单作为 **`--context`** 喂给联合会诊：

   ```powershell
   python tools/glm_consult.py --roles 领域讲解,实现顾问 --question <q.md> `
       --source <文件:起-止> --context <复用检查草稿> --out work/_panel_idea/
   ```

3. 当前模型先对同包留主线判词，再与独立侧对拍，执行仍由当前模型主线负责；
   身份与四栏记录遵循 `model-routing.md`，不为使用旧包装器固定调用 DeepSeek。
