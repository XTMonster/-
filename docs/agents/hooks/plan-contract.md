## 执行计划写作契约（PRD ＋ TDD ＋ 技术方案 三合一）

本次请求被判定为**要产出书面计划／规格**（触发词：`{{HITS}}`）。
按用户裁决（2026-10-05）：**执行计划必须同时是 PRD、TDD 计划与技术方案**，
并且**语言要尽可能减少歧义**。缺任何一节，这份计划都不算完成。

### 0. 硬规矩

1. **术语表先行**：写计划前先给术语表（`术语 → 定义`），**一词一义**；
   全文不得出现同义词混用（例：`镜头/分镜/shot` 只留一个，其余标"旧称"）。
2. **指代必须消解**：不许用"它／那个／上一步那个"；一律写全名
   （`block_director/knowledge/hypergraph.py::parse_query`）。
3. **判据量化**：每条验收都写成 `对象 ＋ 判据 ＋ 阈值 ＋ 分母 ＋ 命令`
   （例：`Q1 top-1 ≥ 0.70，分母＝held-out 条数，命令 python tools/holdout_score.py`）。
   不许出现"更好／更快／尽量"这类不可判定的词。
4. **需求与实现分离**：需求（要什么）与实现（怎么做）分两节；实现不得改写需求。
5. **明确"不做什么"**（Non-goals）：写清本轮**不做**什么，防止范围蔓延。
6. **待裁决项单列**：需要用户拍板的（口径、阈值、许可、范围）列成 `待裁决 D1…Dn`，
   每条写"选项／代价／我的建议"；**不许默许**。

### 1. PRD 区块（要什么）

* **背景与现状**：引用仓库真源（`AGENTS.md` 状态块、`docs/knowledge/ACCEPTANCE_STATUS.md`、
  最近提交）——**给 `文件:行号` 或命令**，不要转述印象。
* **用户需求（原话 + 编号）**：直接把用户这次的原话**逐字引用**，编号 `U1…Un`；
  然后再写"我理解的可验收需求" `R1…Rn`（`Rn` 必须能从 `Un` 推出，且每条可判定）。
  **U → R 的映射要显式写出**（哪条 U 派生出哪几条 R）。
* **用户故事与验收标准**：`作为…我要…以便…` ＋ Given/When/Then 式验收。
* **非目标**（Non-goals）与**已知约束**（本项目硬约束见 `github-reuse.md` §4b）。

### 2. 技术方案区块（怎么做）

* **架构与数据流**：涉及模块、契约、数据形状（字段名/单位）、失败模式与回滚。
* **改动清单**：精确到 `文件:函数`；新接口给**签名**；破坏性改动要给迁移路径。
* **依赖与许可**：新增任何依赖都要写"放哪一层（插件进程／sidecar／构建期）＋ 许可 ＋ 体积"。
* **理论/文献/GitHub 出处**：每条关键设计给**可核对的出处**——
  论文（作者/年份/标题/链接）、官方文档、或 **GitHub 上游**（`owner/repo` ＋
  **commit hash** ＋ 许可证 ＋ 我们用它的哪一部分）。**没有出处的设计要显式标 `无出处（自研）`**。

### 3. 改动别人代码的规划（按需求改，不是迁就上游）

若本轮要用上游代码（依赖／魔改／移植），**必须**按 `github-reuse.md` §4a 写：

| 需求 | 上游现状 | 四档判定 | 改成什么形状 | 改造点（`文件:函数`） | 上游 commit | 许可与差异 |
|---|---|---|---|---|---|---|
| `R1` | … | `①原生满足/②改上游即可满足/③改上游也满足不了/④只有改我们的需求才能用` | 目标接口签名/数据结构 | … | `abc1234` | MIT；patch 或 diff 清单 |

* **④ 按弃用处理**（需求优先，不许把需求打折写成"满足"）。
* 采用/魔改都要给：**上游可跟踪策略**（fork ＋ rebase／维护 patch）、
  **衍生许可**（保留声明与许可证全文；Apache 加 NOTICE；GPL/AGPL 不得引入）、
  **与上游的差异清单**。

### 4. TDD 区块（先写测试，再写实现）

* **测试清单先行**：每个阶段列出用例 `名称 ＋ 断言 ＋ 夹具 ＋ 命令`，
  其中至少一条是**对抗性用例**（证明"做错会被抓住"）。
* **红 → 绿 → 重构**：先让新用例红（附真实失败输出），再实现到绿，再重构；
  每阶段的"绿"要有命令与输出。
* **判据不许动**：不得删测试、跳测试、放宽阈值、改断言（与《强制执行契约》第 4 节同源）。
* **验收链**：本仓库既有链（门①–⑩ ＋ `pytest` ＋ 探针清单）必须**原样**通过；
  若本轮改动了任何判据，**只能由用户裁决**，并在计划里单列。

### 5. 执行顺序与目标（怎么排、什么时候算完）

* **阶段表**：`阶段 → 目标（DoD：可判定的完成定义）→ 依赖 → 串/并行 → 产物 → 验收命令`。
* 每阶段**先写测试、再实现、再跑链**；失败先定位修复，**不许跳到下一阶段**。
* **风险与回退**：每条风险给"触发条件 ＋ 观测方式 ＋ 回退动作"。

### 6. 计划的完成判据（自查清单）

- [ ] 用户原话 `U1…Un` 逐字引用，且与 `R1…Rn` 有显式映射
- [ ] 术语表 ＋ 无指代歧义 ＋ 无"更好/尽量"这类不可判定词
- [ ] PRD / 技术方案 / TDD / 执行顺序与目标 / 出处（含 GitHub 与 commit）五节齐全
- [ ] 若用上游代码：四档判定 + 改造点 + 差异清单 + 许可 + 上游可跟踪策略
- [ ] `待裁决 D1…Dn` 单列，每条有选项与代价
- [ ] 判据一个字没动（或改动已单列待裁）

### 7. 怎么产出这份计划（**由 GLM-5.3 起草 ＋ 默认自我精炼 5 轮**）

专门的计划通道按 `model-routing.md`：默认 **GLM-5.3**，自我精炼 5 次；
主线使用**当前会话选择的模型（不固定）**核对与执行，不再固定 DeepSeek。
历史中转站试验不决定当前主线型号；用户当轮明确更改计划通道时以当轮要求为准。

```powershell
python tools/plan_writer.py --provider glm --question work/_q.md `
    --source <文件:起-止> --context <产物> `
    --out work/_plan/                 # 默认 --rounds 5
```

* **两条通道的差别**：GLM-5.3 是"始终思考"模型，要 `max→high→low` **档位阶梯**才能
  拿到正文，所以 `--level` 对它有意义；中转站**没有档位**（`--level` 只被记账、不被使用），
  实测一次小调用 **4.3 s**、`finish_reason=stop`、正文正常。
* **`gpt6A` 的落地型号 ＝ `gpt-6-astra`**（用户 2026-10-06 亲口确认："就是这个了"）。
  中转站 `/v1/models` 里没有"gpt6A"这个字面量，列出的是 `codex-auto-review`／`gpt-5.5`／
  `gpt-5.6-{luna,sol,terra}`／`gpt-6-astra`／`gpt-6-luna`／`gpt-6-sol`／`gpt-6.1-sol`；
  主线按"唯一以 A 起名的 `gpt-6*`"取了它并得到确认。**要换仍可设 `LINKAI_MODEL`**。
* **一条硬约束**：中转站域名在 Cloudflare 后面，**裸 urllib 的 UA 会被 `403 code 1010`
  挡掉**——客户端 `tools/kb_fetch/llm.py::RelayClient` 已经强制发浏览器 UA，
  谁要绕过它自己写 HTTP 就会撞上这条。

* **每轮都留证**：`plan.md`（最后一轮成功稿）／`plan.round{1..5}.md`／
  `plan.round{r}.usage.json`／`plan.refinements.json`（每轮字数·sha256·usage·耗时·finish_reason）／
  `bundle.manifest.json`（**先写证、再联网**）。
* **prompt 预算（工具会在联网前拒绝超预算的包）**：GLM-5.3 是"始终思考"模型，
  输入越长 reasoning 越长——实测 2026-10-05：**5164 token 的输入在 `low` 档把 32768 个
  completion token 全烧在 reasoning 上（32532）、`finish_reason=length`、正文为空**，白等 460 s。
  安全区是 **~2k token（≈3000 字符）**；超了用 `--status-chars 400`、
  `--context-tail 2000`、缩短 `--question`、只给相关行段来压小。
  （这条是 GLM 侧的实测；中转站侧**未测**它的 reasoning 预算，所以**同一个预算照旧守**——
  超预算的包在两条通道上都会被工具在联网前拒掉。）
* **墙钟预期**：GLM `low` 档一轮实测 6–14 分钟（取决于包大小）；中转站实测一次小调用
  4.3 s，但**写计划的整包没测过**。**默认 6 次调用（1 草案 + 5 轮）在 GLM 上是小时级**
  ——建议后台跑，别在交互里等。
* **精炼不是改需求**：每轮提示词已经把"判据/门限/阈值一个字不许动"写死；
  主线**不许**替模型改需求，只负责核对证据、补齐事实、执行与提交。
* 主线可在两轮之间插意见：`--critique work/_critique_1.md`（第 r 轮用第 r-1 个文件）。
* **一轮失败不丢稿**：空正文/超时只记该轮 `failed`，保留上一轮继续，报告里如实写哪几轮失败。
* **被截断的一轮不采纳**：`finish_reason=length` 记 `truncated` 并保留上一轮
  （实测：精炼轮的 completion 全烧在 reasoning 上，正文只有半截）；
  精炼后**大幅缩水**（< 上一轮 50%）记 `shrink=true` 留痕，供人判断是不是丢了内容。
* 计划到主线手里后：**逐条核对 U→R 映射与出处**（模型的断言不是事实），
  再按第 4 节的 TDD 顺序执行；执行只在主线上做。

`github-reuse.md`，模型分工见 `model-routing.md`。）
